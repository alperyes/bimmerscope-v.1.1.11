See `zy.cs:581`, `zm.cs:154`, `zz.cs:12833`, `zz.cs:12950`. These references alone do not identify every supported cable, endpoint, or on-wire diagnostic command.

## Interpretation and limits

The APK includes a real write workflow and an S55 type; it is not merely a tuning UI. The code also distinguishes map-only versus full OEM writes and one-pass versus two-pass cases. These are **code structure findings**. Their exact vehicle-side meaning, branch conditions, data dependencies, and recovery behavior still require tracing.

The main managed assembly has deliberate control-flow and string obfuscation. Decompiled class names such as `zz`, `xn`, and `yy` are not original source names. The vehicle's software and unlock state are still unverified.

## Additional programming-path evidence (12 October 2026)

The following are **static code findings**, not observed S55 vehicle traffic:

- S55's `yy` type inherits `@as`, whose constructor sets `Platform.FG` (`yy.cs:3`, `as.cs:49`). The shared F/G authorization path `zz.v(ref string)` delegates to `zz.b(ref string)` (`zz.cs:26522`, `zz.cs:26592`). `b(ref string)` includes a conditional sequence that sends extended session `10 03`, reads DID `10 0A`, then sends `85 02`, `28 01 01`, `31 01 10 03 01`, `10 01`, `10 03`, and `10 02`. It checks for a `50 02` response and has retry and unlock-state branches (`zz.cs:51394-51620`). The code does not prove that every S55 write takes every branch.
- A separate function constructs a `27` seed request with subfunction supplied by its caller, then a key request with subfunction plus one. Its observed call site uses `17` decimal (`0x11`), so that branch is `27 11` followed by `27 12` when the key step is reached (`zz.cs:51483`, `zz.cs:51776-52000`). The key calculation or supplier has not been validated.
- A shared erase function uses `31` RoutineControl, checks for a `71` reply, and reports `NOERASE_MEM` on failure. For F/G it obtains a request from `ap().b(SWLayer)` (`zz.cs:27398-27580`). The S55 `yy` class inherits `@as` without overriding its erase fields (`yy.cs:3-15`). The `@as` request builder copies a four-byte layer selector into `31 01 FF 00 02 40 ....` (`as.cs:33-39`, `as.cs:599-684`). This yields `31 01 FF 00 02 40 80 00 FD 00` for BTLD, `31 01 FF 00 02 40 80 3F FD 00` for PRG, and `31 01 FF 00 02 40 80 1F FD 00` for CAL. These are request templates in the APK, not captured S55 traffic. The layer selectors' precise ECU-side meaning and successful-response conditions still need validation.
- The shared transfer method `zz.b(byte[], uint, int, uint, int, int, bool)` clones request templates `aw.s` and `aw.p`, inserts an address and length into the download request, constructs `36` data packets with a sequence byte, checks acknowledgement and retry conditions, then sends the transfer-exit template (`zz.cs:27920-28780`). Its response checks include `74` for download acceptance, `76` for data packets, and `77` for transfer exit (`zz.cs:28058`, `zz.cs:28421`, `zz.cs:28448`). The `zs` template defines `34 80 ...` and `37 80 ...`; `zt` defines `34 00 44 ...` and `37` (`zs.cs:18-39`, `zt.cs:18-34`). Which template a particular S55 connection selects still needs proof.
- The template choice is made during connection probing rather than by `ECUTYPE.S55` alone. The `z6.j` probe starts with `1A 80` and can fall back to `3E 00`; it sets `z3.a` after a positive reply to the former and `z3.z` after a positive reply to the latter (`z6.cs:211-215`, `z6.cs:307-315`, `z6.cs:439-446`, `z6.cs:491-501`). The `zz` connection state machine assigns `zs` for `z3.a` and `zt` for `z3.z` (`zz.cs:12739-12748`, `zz.cs:12772-12775`, `zz.cs:12918-12921`, `zz.cs:13120-13127`). This explains the two download formats, but a matching capture or full reachable-path trace is still needed to prove which reply and template the target S55 uses.
- A higher-level section writer calls F/G authorization via `v(ref string)` and passes section data, start address and length into the shared transfer method (`zz.cs:25600-25730`). The app therefore has concrete programming primitives in the APK, although the complete S55 path from selected map to final verification is still unresolved.
- On an F/G ECU, the post-transfer `t(byte)` method delegates to `a(byte)` (`zz.cs:28782-28869`). That method builds a 12-byte `31 01 02 02 12 40 ... 00 00` routine request and inserts a layer selector (`zz.cs:52204-52466`). Argument `0` inserts BTLD selector `80 00 FD 00`, `2` inserts PRG selector `80 3F FD 00`, and `4` inserts CAL selector `80 1F FD 00`; it requires a five-byte reply beginning `71` and inspects a status byte (`zz.cs:52339-52445`). Depending on state it also sends `31 01 FF 01` and checks that reply (`zz.cs:52424-52452`). A higher-level writer calls `t(0)` after one transfer, then sends `11 01`, waits two seconds, and re-enters authorization (`zz.cs:25777-25805`). Another writer has a similar `t(0)`/reset branch with a five-second wait (`zz.cs:26019-26029`). These paths are conditional; their exact reachability for a selected S55 map has not yet been established.
- The main write controller partitions selected image data into BTLD, PRG, CAL, and Hack groups (`zz.cs:13954-13957`). It has distinct erase calls for BTLD (`zz.cs:14457`, `14879`), PRG (`zz.cs:14833`), and CAL (`zz.cs:14819`, `15150`); section transfers for the respective groups (`zz.cs:14498`, `14986`, `15221`); and post-transfer `t(...)` calls for BTLD, PRG, and CAL (`zz.cs:14539`, `15026`, `15270`). This supports a multi-layer programming controller, but the obfuscated control flow and `FlashWriteType` conditions prevent treating every listed call as one unconditional order.

This is **not yet a validated end-to-end S55 flash sequence**. In particular, the path selection for the actual 2014 F82 software, security result, erase parameters, image selection, checksum method, and recovery flow remain unverified. Do not use these code fragments as a flashing recipe.

## Follow-up trace: UI entry and platform classification

The decompiled `xn` class has a static `zz` engine instance (`xn.cs:2589`, initialized at `xn.cs:2629`). The `xn.b(bool)` method at `xn.cs:4356` only toggles the busy indicator; it is not the write operation.

The matching `zz.b(string, bool)` at `zz.cs:25415-25436` stores the selected string in `m_b0`, stores the boolean in static field `zz.i`, and schedules `bl()`. The classifier contains explicit rejection paths such as software mismatch and wrong binary size (`zz.cs:6726`, `6849`, `6915`, `7047`) and branches on installed MHD state and hardware number (`zz.cs:8220-8260`). Which of those paths is reachable for a particular S55 software combination remains unresolved because the control flow is heavily obfuscated. ## Transfer constructor details (13 October 2026)

The map-write stage is now linked to the controller: `al()` is true for `Map_OEM`, `Map_Tuned`, and `MapTwoPasses_Tuned` (`zz.cs:16514-16568`). The controller skips the program/bootloader stage when `al()` is true (`zz.cs:14378-14385`) and jumps to its CAL path (`zz.cs:15573-15576`), which erases CAL (`zz.cs:15150`), loops over CAL sections (`zz.cs:15192-15230`), and calls `t(4)` (`zz.cs:15270`). Thus a classified S55 map write follows session/security preparation → CAL erase → CAL download/data/exit per section → CAL status checks, without passing through the full-write BTLD/PRG branch. The inherited S55 CAL section builder returns two inclusive ranges: `0x80180000–0x801FFBFF` (523,264 bytes) and `0x801FFD00–0x801FFFFF` (768 bytes) (`as.cs:322-327`). This is the generic F/G builder used by `yy`; `zz.b(@as,SWLayer,...)` delegates to that builder (`zz.cs:69882-69898`). Image transformation, compression, and post-builder processing may affect the transmitted bytes, so these ranges are section definitions rather than a verified on-wire download.

The main controller sets its pass count to two only for `TwoPassMHD` or `MapTwoPasses_Tuned`; all other write classifications set it to one (`zz.cs:13623`). Pass index starts at zero (`zz.cs:13624`). Preparation mode starts as `z0.z`; the first pass of a two-pass write changes it to `z0.a`, while a one-pass OEM write changes it to `z0.b` (`zz.cs:13634-13683`). `an()` means exactly `Map_OEM` or `Full_OEM` (`zz.cs:16486-16511`). After each pass, the controller increments the index (`zz.cs:15327-15330`). Thus the code establishes classification-driven passes, rather than every write blindly running two passes. The meaning of `z0.a` inside image generation and which classification the target image receives remain to be traced.

S55 inherits subtype `zq.b.b` from `@as` (`as.cs:64`, `yy.cs:3-15`). In the classifier's installation branch, missing MHD installation or a hardware-number mismatch leads to `OnepassMHD` (`zz.cs:8206-8231`). The immediately following F/G upgrade to `TwoPassMHD` is restricted to subtypes `zq.b.z` or `zq.b.a` and a bootloader condition (`zz.cs:8270-8318`); the later map/two-pass upgrade is restricted to subtype `zq.b.y` (`zz.cs:8525-8585`). Those subtype conditions do not match the S55 constructor's `zq.b.b`. This rules out those particular automatic two-pass branches for the normal S55 object, without proving all possible S55 writes are one-pass. If MHD is already installed and hardware matches, the classifier additionally compares MHD image/version information and can select `OnepassMHD` when it differs (`zz.cs:8351-8403`); the definitions of the compared values still need tracing.

The classifier starts with `w = bu()`, copies that to desired value `v`, and obtains its initial type from `b(ref z0, ref string)` (`zz.cs:6413-6415`). That helper defaults a non-OEM request to `Map_Tuned`; OEM mode yields `Map_OEM` for program-status values 6 or 15, otherwise `Full_OEM` (`zz.cs:24922-25004`). ## Method notes
